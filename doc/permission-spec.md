# Permission System

Permissions control what an agent may do and where. They belong to a session, not to a device, account token, or directory shared across sessions.

## Owner and room users

An authenticated owner is the owner whether accessing their Linggen locally or remotely, including through a browser. Owner sessions use the permissions below.

A room user running Linggen on their own device uses their own device's permissions; sharing a model or token does not give them control of the owner's device. Room browser consumers currently have capabilities limited by the owner's room configuration and cannot approve additional permissions. The intended simpler browser-chatter model is **chat only**, with no permission prompts; it is not yet established here as implemented. See `room-spec.md` for the current room model.

## Remote trust: devices and memory

Anything reaching this machine over the network presents a paired device's token at the LAN gate. Each paired device is one row with a kind:

- **Machine** — the owner's other computer, approved with Allow at this machine. For memory it is the owner: it sees all of the owner's memory, through `/mcp/memory` and the replica protocol.
- **Phone** — paired with the on-screen code. For memory it is its own person and sees only that person's rows, through `/api/memory/<verb>`; the machine routes refuse it.

Through the WebRTC tunnel a request arrives from loopback, so the tunnel names the device it carries and marks what it knows of a peer that names none; only this machine's own page and the owner's relay login count as the owner. Every request is sent as the person behind the device, resolved as memory resolves it, whatever `user_id` it names, and one naming a session that is not that person's (`session_id` or `session`, in the query or the body; § A session is its person's) is refused with 403: by the tunnel for a peer, by the LAN gate for a token on plain HTTP — one function for both. A body the gate cannot read as JSON passes through as it came. Loopback keeps trusting its caller. Approving a machine (Allow / Deny) is only for someone at this machine. See `memory-spec.md` § Who reaches memory.

The same kinds decide two more doors. The MCP front door (`/mcp`) is for computers: its tools act as the owner, so this machine and an approved machine come in and a phone is refused (403). `/api/ling-mem/config` (memory's keep-days and recall threshold) answers the owner rule only: this machine and an approved machine; a phone and a caller nobody knows get 403. `GET /api/user/name` answers with the asker's own name: core memory's for the owner, the pairing record's for a phone that is another person, none for a signed-out phone, and 403 for a caller nobody knows.

A phone names its device as its channel opens, and its first requests can overtake that message. A request from a peer that has not named itself waits up to 1.5 s, counted from the peer's first request, for the name to arrive.

### A paired device's standing follows its account

A paired device stands at a level on the ladder sessions use — chat < read < edit < admin — and at most that level reaches this machine through it (`server::person::standing_of`, one answer for a request, a control frame, the media channel and a session stream):

- **The owner's device stands at admin.** An approved machine is the owner's. A phone is the owner's when its account claim is verified as this machine's own account: the relay checks the account credential the phone sends beside its device grant (`x-linggen-account`) and says in the offer (`owner: true`) whether that account owns this instance; at `identify` the claim of this machine's account is then kept as verified on the device row (`verified_account`). A claim alone never verifies. A different claim, or signing out, clears it; a reconnect with no relay (the LAN, no internet) keeps it while the claim stays.
- **Any other device stands at the level set for it at this machine** — chat, read or edit; read when none is set; admin is the owner's alone. Its person is its account, or its device when it is signed out, claims this machine's account unverified, or claims an id that is not an account's own (none, this machine's owner's, no one's, a device's). Who a device is comes from one place (`server::person::of_device`); the strings a person is kept as — in a session's meta, a memory row, a URL, an event — are read and written only by `server::person::Person`. The level is set by `PUT /api/pair/devices/{id}/permission`, only by someone at this machine (never from a paired device or another machine), and kept across a re-pair.
- **A peer that has named no device** is the owner at admin only when the tunnel knows it as the owner (this machine's page, the owner's relay login), else no one: it reaches only the way in — health, pairing's bootstrap, the page's shared files and page files — and anything else is refused (`403 {"error":"unnamed"}`). On the LAN a peer cannot open a channel without a paired device's token, so it is named from the start.
- **A phone out of step** with this machine's contract number (`webrtc-spec.md` § Contract number) stands at chat at most.

Each route declares its class beside the routes (`server/routes/classes.rs`): chat, read, edit, admin, or **own** — a device's own records, reached at any level. A route not declared is admin, and a lock test fails until a new route has its class. A request whose route is above its caller's level is refused with `403 {"error":"beyond_level","level":"read","needs":"edit"}` — a fact; the companion words it. The level rides on to the handler (`x-linggen-level`; absent means this machine) for what a handler judges within its route: a skill tool called through the page's door is judged by its tier against the lower of the skill's own grant and the caller's level, while the model's own call is unchanged; a device below admin revokes only itself.

What a device at **read** may do: talk in its own chat and day, its own memory rows, push registration, presence, facts and topics, list a sync folder, the read doors (a skill page's files, its declared read tools), and what this machine offers (models, skills, status). Refused by intent at read: clearing a chat and answering plans or questions, hand-offs to the Mac, queueing downloads, syncing edits, photos, a skill's save, setting the Mac's language or config, the raw shell route. Edit opens those writes; the Mac's own settings, files, shell, every session's work, accounts, rooms, devices and memory's own routes stay admin. Below admin a peer is streamed, sent events for and shown in page state only its own person's sessions. A room consumer keeps its room's own rules.

Presence (`/api/presence`) is the owner's: another person's surface, or no one, says nothing of whether the owner is here. Only a peer at the owner's standing sets the chat an agent's message lands in (the page's focused session).

**A session is its person's.** Whose a session is comes from one place, its meta's `user_id` (the person the session was made for; none, or this machine, is the owner), read by `server::day_session::may_enter` — the rule the seam asks for every session a request names, and every route that finds its session from another id (a question, a run, a queued message), the session streams and page state. The owner enters every session. Any other person enters their own day and the sessions made for them; a session id not kept yet is theirs to make; another person's session, a session named by an id no session has, and a run of no session are refused (`403 {"error":"that session is another person's"}`). A peer that has named no device enters no kept session. A room consumer is its own account; one whose id is not an account's own (none, this machine's owner's, no one's, a device's) is no one.

**A turn runs at its device's level.** What a device's chat turn may do is its level too, through the session spec's ceiling (`session-spec.md` § A turn's ceiling): an action above it is refused and never asked for, whatever the session's grants; the model is told the action needs more than the device stands at. Such a turn asks no one, carries none of the owner's memory, and runs no MCP tool ungated. Under a ceiling Linggen's own folder — its settings, its credentials, every session's record — is the owner's alone: nothing in it is reached, whatever the session's grants or a skill's cover, but the session's own folder, read.

**This machine's models and keys are the owner's.** `GET /api/pair/me` gives the owner's device every model allow-listed for it, a provider's key riding along (`kind: byok`); any other device only the models it reaches with its own credentials (Linggen Cloud, a ChatGPT sign-in) and no key. A device verified as the owner's later gets them at its next sync; one that stops being the owner's is sent none, and the phone deletes every key the Mac no longer sends at that sync. The inference channel (running on this machine's models) is the owner's and a linggen room consumer's; any other peer is refused with `{"error":"beyond_level","level":…,"needs":"admin"}`.


## Session grants

Each grant pairs a permission level with a scope: a directory and its children, or **all directories** (`*`). The most specific directory grant takes precedence; the all-directories grant is the fallback. Without a matching grant, the level is `chat`.

| Level | Agent capability |
|:---|:---|
| **chat** | Conversation and chat-tier capabilities; gated actions require permission. |
| **read** | Read-class tools and commands. |
| **edit** | Read plus file editing and other edit-class actions. |
| **admin** | Edit plus admin-class actions, including higher-risk commands. |

These levels apply uniformly to individual directories and all directories. All-directories admin is broad access, not macOS administrator or root privilege. The system's hardcoded deny floor still blocks certain dangerous agent commands regardless of grants. The floor judges the program a command really runs: named by any path (`/usr/bin/sudo`), after `NAME=value` words, or behind a program that only runs what follows it (`env`, `command`, `exec`, `nohup`, `nice`, `time`). It is a tripwire for the plain forms of a catastrophe, not a sandbox: what a script or a build tool does once it runs is not read.

**Grants are kept per place.** A session's turns each stand in a place — the app whose page the turn came from, or home (`session-spec.md` § A turn's place) — and each place has its own grants in the session's permission file: a grant the user gave while in one app is not honoured in another app's turn of the same session, and is still honoured when a turn is back in the first app. The session's own place (its skill, or home) keeps its grants where the file always held them, so a file written before places reads as the grants of the session's own place; another place's grants sit under that place's name. A subagent uses the grants of the place its parent's turn stands in. The permission modes and the hardcoded deny floor are the same in every place. Today every turn of a session stands in the session's own place, so a session has one set of grants in practice; the badge, the per-chat grants and `agent_permit` show and change that set.

A new user session starts with the configured default level on its starting directory, normally `read`. A place's first turn in a session starts the same way, on the place's folder. Session grants survive reopening the same session; they are not automatically inherited from another session. Missions and skills may provide their own grants. Skills may also persist and reapply user-configured grants across sessions; this is distinct from inheriting another session's grants.

## Outward commands

A command whose effect is off this machine, where the path check cannot see it and from where it cannot be undone, is asked whatever the session's grants — admin on its folder or on all directories included. It is asked of whoever answers for the session (the person; the caller of a delegated run; refused at once when nobody can answer), and one answer covers that one command: the only choices are allow once and deny, never a grant. The deny floor is checked first. When the command also needs a level the grants do not give (a path outside them), that need is part of the same one-time ask. The kinds, kept in one table:

- **Publishing:** `cargo publish`; `npm`, `pnpm`, `yarn`, `bun publish`; `gh release create|edit|upload|delete`; `gh pr merge`; `flutter pub publish`, `dart pub publish`; `docker push`, `podman push`; `gem push`; `twine upload`; `pod trunk push`.
- **Remote operation:** `ssh`, `scp`, `sftp`; `rsync` with a remote operand (`host:path`, `rsync://`); the cloud and deploy command lines `aws`, `gcloud`, `az`, `kubectl`, `helm`, `terraform`, `pulumi`, `wrangler`, `vercel`, `netlify`, `fly`, `flyctl`, `heroku`, `firebase` — on every use, read-only ones (`kubectl get`) included, as those are too many to tell apart.
- **A push that is more than a plain push:** `git push` that names `main` or `master` as a destination (`origin main`, `HEAD:main`, `x:refs/heads/master`), forces (`-f`, `--force`, `--force-with-lease`, a `+refspec`), deletes (`--delete`, `-d`, `--prune`, a `:branch` refspec), or pushes `--mirror` / `--all`. A plain `git push`, `git push origin <another branch>`, `git push -u origin <branch>` and `git push --tags` are not asked.

The program is found as the floor finds it — by its file name whatever path it was run by, past `NAME=value` words and the programs that only run what follows — and its subcommand past the options before it (`gh -R o/r pr merge`, `git -C dir push -f`). A command that only names such a program (`echo ssh`, `man scp`, `git commit -m "publish"`) is not asked. Like the floor, it is a tripwire for the plain forms, not a sandbox: a script, a build tool or a shell given the command as text can still do the same thing.

## Coding sessions

A session whose work is `code` (the `work: code` tag of `session-spec.md` — the Coding switch, or an `agent_run` with a `write_dir`) runs any program in its own folder without asking. In the Bash check, a command segment the tables would ask admin for is judged at edit: an unknown program (`rustc`, `flutter`, `./tool`, a program by its absolute path), and the session's ordinary work that the tables hold back elsewhere (`rm`, `chmod`, `kill`, `python3 x.py`, `bash build.sh`, a `git` or `cargo` subcommand outside the tables). The program is the one really run, past `NAME=value` words and the programs that only run what follows (`RUST_LOG=debug cargo test`, `time cargo test`, `nice …`), found as the deny floor finds it. Three kinds stay with the tables, in a coding session as in any other: a program that acts beyond the folder — another user's rights (`sudo`, `su`), sending to the network (`curl`, `wget`, `nc`), the system's packages, containers, services and other apps (`brew`, `docker`, `launchctl`, `osascript`, …), one table in `classify.rs`; code handed over as text rather than as a file (`sh -c '…'`, `python3 -c`, `node -e`, `git -c …`, `eval`, `xargs`), which no check here can read; and dynamic syntax. The deny floor and § Outward commands come first; edit is still needed where the command runs (its own file and a scratch path do not stand in for that); every path the command names is still judged, whatever wraps it. A `Task` child of a coding session is one too. The gate reads the session's tag at each check: turning Coding off takes it away at the next one (turning it on, at the next turn). An app's session, the daily session, a companion's and a mission never are coding sessions. The honest limit: such a session already runs whatever code its folder holds (`cargo run`, package scripts, tests) as the owner; this does not confine what that code touches, and the table of programs beyond the folder is a tripwire for the plain forms, not a sandbox.

## Asking for permission

When an interactive agent action needs a higher level, the chat asks the current session's user. The request names the action and shows the target path. It offers the needed level on each directory from the repository root down to the file's directory, so one click can cover the whole repository:

- **Needed level on a directory**, one button per directory. For `a/b/c/file`, the buttons are `a`, `a/b`, and `a/b/c`.
- **Needed level everywhere**.
- **Admin everywhere**, added only when the needed level is below admin.
- **Deny**.

An outward command offers only **Allow once** and **Deny** (§ Outward commands). An admin action omits the extra admin choice. A path with no repository root stops before the home directory. `/` and system directories such as `/dev` are not offered.

Deny blocks this action and closes its project (the nearest git root, else its folder; never the home folder) to every tool for the rest of the run: a later call there is refused without asking, the chat shows one line saying so, and the agent is told to mark what needed it unverified and continue. Nothing is stored: the next run asks again. Either allow choice is written to that session's permission file. Reopening the same session keeps it. Other sessions do not inherit it. A grant for all directories replaces existing directory grants; a later, more specific directory grant can override it. Admin everywhere is the broad setting: later actions in that session are not asked again. The hardcoded deny floor still blocks dangerous commands. Unattended runs cannot ask and must pause or fail when permission is insufficient.

### Sessions that ask their caller

A session started through MCP `agent_run` has no person in the chat, but it has a caller. An action beyond its grants asks the caller instead of failing: the request (action, target path, needed level, the agent's stated reason) waits on the session's wait stream and in `agent_status`, and the run waits for `agent_permit`. The caller may allow the action once, grant its path or its folder at that level for the rest of the session, or deny; a deny closes the project for the run as above. The caller is never offered a grant for all directories, and for an outward command (§ Outward commands) only allow once or deny: the request says `outward`, and `allow_session` is refused with a plain error. No answer within 10 minutes counts as deny. A refused action is listed as denied. The hardcoded deny floor is never asked. The owner sees the same request in the chat and may answer it there.

The chat shows the effective level for the current working directory. Changing that directory updates the displayed level without changing the grants. Changing its level affects that directory, not unrelated directories.

## Boundaries and exceptions

- Reading outside a grant also requires approval; reads are not universally free. Temporary scratch directories are exempt from path-mode checks, but not the Bash deny floor: the path is free, the command is not — one that runs code (`sh /tmp/x.sh`, `python3 -c … > /tmp/out`) with no other path to judge is judged at the session's folder, like a command with no path. A session may read its own session folder (its background tasks' logs) without a grant; writing there, or reading another session's folder, is gated as usual.
- Bash commands are classified by risk and checked against identifiable targets. This is **best effort, not a filesystem sandbox**: a command may access files, processes, or network resources beyond what can be inferred from its arguments. A directory-scoped admin grant must not be presented as shell confinement. Text a command carries is not a target: a heredoc body fed to `cat` or `tee`, and the pattern or program of `grep`, `rg`, `sed`, `awk`, `jq` and `git grep` (also behind `git -C <dir>`; the words after its pattern are revisions or pathspecs, judged as paths; any other option before `grep`, or a `(` or `)` word, keeps every word judged). Only a shape the gate reads exactly as the shell does is dropped: a body any other program reads, one the shell expands (`$`, backticks under an unquoted delimiter), or one in a command where any line outside the bodies holds a pipe into the reader, grouping, a comment, a substitution, a backslash, a compound command (`if`, `while`, `{`), an assignment or a builtin that changes the shell (`alias`, `exec`, `eval`) is still judged, and so is every word of a pattern command whose flags it cannot read. A flag counts as taking a value only when every implementation takes one (BSD `sed -l` and `grep --context` do not; BSD `sed -i ''` is not read specially, as GNU sed takes the word after it as a file). A command with a heredoc left in, with a quote character or backslash inside a comment, or with unquoted whitespace the shell does not split on (a carriage return, a no-break space), is unclear — its words are not the shell's — and is judged as admin. A `sed` or `awk` script that names a file itself (`w file`, `r file`, `print > "file"`, `getline < "file"`) is judged as admin, like one that runs a command: that file is not a target the gate can see. Where seds and awks disagree on which word is the script (BSD `sed -l`, a bare `-i` on macOS, `awk --assign x` under the one-true-awk), the command is admin or every candidate word is read as the script. A redirect target, glued to its operator or not (`>/x`, `2>>/x`, `</x`), and a file argument are always targets; `/dev/null` and the standard streams are not files.
- A command whose words are decided at run time — a `$` or a backtick outside single quotes — cannot be read, and asks for admin. One variable is read as the shell reads it: `$HOME` and `${HOME}` are replaced by the home folder before the command is judged, so `ls "$HOME/notes"` is a read of that folder. Not when the command sets `HOME` anywhere, or the home path holds a character the shell treats specially. `$?` and `${?}`, the last exit status, are read as a number where nothing is glued to them: they end their word (or their double-quoted string), the word before them holds only letters, digits and `_=:,+@%`, and they do not stand where a program is named (`echo EXIT=$?`, `"rc $?"`). Any other variable, or `$?` in any other place, keeps the command unreadable.
- A program named by a path requires read on its own file; that file alone does not substitute for checking the full command level where it runs. For plain `cp`, `rsync`, `install` and `ln -s` commands with unambiguous operands and safe options, sources require read and the destination requires the command's level; unclear forms retain the full-level check on every operand. A move (`mv`) and a hard link (`ln` without `-s`) keep the full check on the source: one removes it, the other makes a second name for the same file.
- Skills and some chat-tier or explicitly ungated MCP tools can operate outside the ordinary path-mode gate. A skill may request its own grants. The owner should not assume that `chat` alone is a complete isolation boundary.
- Browser actions use site trust and separate confirmations for sensitive actions; see `browser-control-spec.md`.
- Agent permissions do not gate the owner's own typed commands or deterministic skill interface actions. This is not a substitute for enforcing identity and access boundaries on remote interfaces.
- A chat has one set of grants for each place (§ Session grants). Subagents at every depth use the set of their parent turn's place live instead of keeping their own copy. A subagent's permission prompt asks the person for the chat, and a grant made there applies at once to the main chat, the badge and every subagent. A subagent can never raise a grant without the person. A delegated run with no session to share runs on a copy of its parent's grants.
